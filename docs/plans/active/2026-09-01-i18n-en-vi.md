# Execution Plan: Bilingual Support (English + Vietnamese)

Date: 2026-09-01

## Status

Active

## Outcome

The entire site is available in English and Vietnamese under fully
locale-prefixed routes: `/en/*` (English, the default locale) and `/vi/*`
(Vietnamese). Every legacy unprefixed URL (`/`, `/blog`, `/blog/:slug`,
`/internal-project`) permanently redirects to its `/en/*` equivalent so no
existing inbound link or search-engine-indexed URL 404s.

Every user-facing string renders in the active locale: navigation, footer,
command menu, panel/section titles, `sr-only` accessibility labels, profile
prose (bio, about, FAQ, experiences, projects, awards, certifications), the blog
listing chrome, and the error / not-found pages. A visible language switcher in
the header toggles locales while preserving the current path and hash.

SEO surfaces reflect the active locale: `<html lang>`, `hreflang` alternates
(`en`, `vi`, `x-default`), JSON-LD `inLanguage`, canonical URLs, and per-locale
entries in the sitemap. Blog posts are paired across locales so each post links
to its translation and the listing shows only the active locale (with graceful
fallback for posts that exist in one language only).

The site builds, type-checks, lints, and format-checks clean, and a manual smoke
of `/en` and `/vi` passes.

## Context

### Framework and current i18n state

- Next.js 16 App Router (Turbopack), React 19.2, Tailwind v4. Package manager is
  `pnpm@10`; Node 24.
- There is **no** `src/middleware.ts` and **no** i18n today. `src/app/layout.tsx`
  hardcodes `<html lang="en">` (line 134) and `getWebSiteJsonLd()` hardcodes
  `inLanguage: "en"` (line 26).
- `next.config.ts` already defines `rewrites()` (blog `.mdx` raw routes),
  `images.remotePatterns`, and `transpilePackages: ["next-mdx-remote"]`. Any
  plugin wrapper must compose with these, not replace them.

### Route inventory

Localized (must move under `[locale]`):

- `src/app/(app)/(root)/page.tsx` — homepage (renders all profile sections +
  ProfilePage & FAQPage JSON-LD).
- `src/app/(app)/(docs)/blog/page.tsx` — blog listing.
- `src/app/(app)/(docs)/blog/[slug]/page.tsx` — blog post.
- `src/app/(app)/(docs)/blog/not-found.tsx` — blog 404.
- `src/app/(app)/internal-project/page.tsx`.
- `src/app/(app)/layout.tsx` — SiteHeader / main / SiteFooter / ScrollTop.
- `src/app/not-found.tsx` — global 404.

Must stay language-neutral at `src/app/` root (NOT under `[locale]`):

- `(llms)/*` (`llms.txt`, `llms-full.txt`, `about.md`, `projects.md`,
  `experience.md`, `awards.md`, `certifications.md`, `blog.mdx/[slug]`),
  `og/*`, `rss/route.ts`, `vcard/route.ts`, `sitemap.ts`, `manifest.ts`,
  `robots.ts`.

   EN-only `ai-ecommerce-case-study.mdx`. `features/blog/data/posts.ts` reads the
   folder flat by slug with no locale or translation-pair concept.

### SEO constraints

- The homepage emits **ProfilePage** and **FAQPage** JSON-LD from
  `(app)/(root)/page.tsx`. The FAQ is rendered as visible content AND emitted as
  schema from the **same** `FAQ` array — Google forbids FAQPage schema whose
  answers are absent from the page, so the localized FAQ must feed both from one
  source.
- `knowsLanguage: ["Vietnamese", "English"]` and the bilingual `alternateName`
  (`Trương Nguyễn Anh Khoa`) already exist and must be preserved.
- An active SEO/GEO effort exists
  (`docs/plans/active/2026-08-01-seo-geo-name-dominance.md`); the `always`
  prefix strategy changes English URLs, so 301 redirects from the old paths are
  mandatory to retain ranking.

### Chosen library

`next-intl`. Rationale: App Router-native locale routing, `generateStaticParams`
for static rendering of both locales, and a client message provider — required
because several surfaces are client components (`command-menu`, `mobile-nav`,
`desktop-nav`, `toggle-theme`, `scroll-top`). A hand-rolled dictionary would
mean reinventing the middleware, navigation helpers, and provider; YAGNI says
don't.

## Scope

In scope:

- Add `next-intl` with locales `['en','vi']`, `defaultLocale: 'en'`,
  `localePrefix: 'always'` (both locales prefixed: `/en/*`, `/vi/*`).
- 301 redirects from every legacy unprefixed route to `/en/*`.
- `src/i18n/` (routing config, request config, navigation helpers, `Locale`
  type, `Localized<T>` helper + resolver).
- `[locale]` route segment wrapping the `(app)` group; a `[locale]` layout that
  sets `<html lang>` and provides messages.
- Message catalogs `src/messages/{en,vi}.json` for all UI-chrome strings.
- Localize prose data files via `Localized<T>`; update all consumers to resolve
  against the active locale.
- Locale-aware SEO: dynamic `<html lang>`, `hreflang`/`x-default` alternates,
  canonical per locale, JSON-LD `inLanguage`, per-locale sitemap entries.
- Blog locale pairing (frontmatter `locale` + `translationKey`), locale-filtered
  listing, and a translation link per post.
- Language switcher in the site header preserving path + hash.
- Localize `not-found.tsx` and blog `not-found.tsx`.

Out of scope:

- Localizing machine/SEO endpoints (`(llms)/*`, `rss`, `vcard`, `og`,
  `manifest`, `robots`). They stay English-by-contract this pass; a follow-up
  can localize `llms`/`og` if wanted.
- Translating blog article bodies that have no counterpart yet
  (`ai-ecommerce-case-study.mdx` stays EN-only and falls back).
- Auto-translation tooling or a CMS. Vietnamese prose is authored by the user;
  this plan wires the mechanism and seeds `vi` values with English text plus
  `TODO(i18n)` markers where a human translation is pending.
- Number/date/currency formatting changes and RTL (both locales are LTR; dates
  already use `dayjs`/`date-fns` and need no locale split this pass).

## Approach

Smallest coherent sequence. Land the routing skeleton and redirects first (the
only hard-to-revert step, committed on its own), then chrome strings, then a
single data-file vertical slice to prove the `Localized<T>` shape, then the rest
of the data, then SEO, then blog pairing, then the switcher.

### 1. Install and configure next-intl

- `pnpm add next-intl`.
- `src/i18n/routing.ts`:
  ```ts
  import { defineRouting } from "next-intl/routing";
  export const routing = defineRouting({
    locales: ["en", "vi"],
    defaultLocale: "en",
    localePrefix: "always",
  });
  export type Locale = (typeof routing.locales)[number];
  ```
- `src/i18n/navigation.ts`: re-export `Link`, `redirect`, `usePathname`,
  `useRouter`, `getPathname` from `createNavigation(routing)`. All internal
  navigation must import from here so locale prefixes are handled automatically.
- `src/i18n/request.ts`: `getRequestConfig` that validates the incoming locale
  against `routing.locales` and loads `../messages/${locale}.json`.
- `next.config.ts`: wrap the existing config with
  `createNextIntlPlugin("./src/i18n/request.ts")` — preserve `rewrites`,
  `images`, `transpilePackages`, `turbopack`, `reactStrictMode`,
  `devIndicators`.
- `src/middleware.ts`: next-intl middleware from `routing`, with a matcher that
  runs ONLY on localizable paths and explicitly skips machine routes and assets:
  ```ts
  export const config = {
    matcher: [
      "/((?!api|_next|_vercel|og|rss|vcard|llms\\.txt|llms-full\\.txt|.*\\.md|.*\\.mdx|sitemap\\.xml|robots\\.txt|manifest\\.webmanifest|favicon\\.ico|images|audio|fonts|.*\\..*).*)",
    ],
  };
  ```
  (Tune against the real asset paths under `public/` during implementation;
  verify each machine route is untouched.)

### 2. Restructure routes under `[locale]` + redirects

- Move `src/app/(app)/` → `src/app/[locale]/(app)/`.
- Add `src/app/[locale]/layout.tsx`:
  - `generateStaticParams` returns `routing.locales.map(locale => ({ locale }))`.
  - Validate the param with `hasLocale(routing.locales, locale)`; call
    `notFound()` otherwise.
  - `setRequestLocale(locale)` for static rendering.
  - Render `<NextIntlClientProvider>` around `children` so client components
    (`command-menu`, `mobile-nav`) get messages.
- Split `<html>`: the current global `src/app/layout.tsx` keeps the fonts,
  `<head>` scripts (dark-mode + macOS detection), and `<body>`, but `lang` moves
  to be driven by the active locale. Concretely, set `<html lang={locale}>` in
  the `[locale]` layout; if Next requires the single root `<html>`, keep a
  minimal root `layout.tsx` and set `lang` via the locale param passed down.
  Decide the exact split during step 2 and record it in Decisions.
- Legacy redirects: add to `next.config.ts` `redirects()` (permanent/301):
  `/` → `/en`, `/blog` → `/en/blog`, `/blog/:slug` → `/en/blog/:slug`,
  `/internal-project` → `/en/internal-project`. Keep the existing `.mdx`
  `rewrites` working (they target machine routes, not localized ones).

### 3. Extract UI-chrome strings to message catalogs

- Create `src/messages/en.json` and `src/messages/vi.json` with namespaces:
  - `nav` — `portfolio`, `blog`.
  - `footer` — `inspiredBy`, `builtBy` (with a `<github>` rich-text chunk).
  - `commandMenu` — group headings, item labels, `placeholder`, `empty`,
    footer action labels, toast messages.
  - `panels` — `about`, `stack`, `experience`, `projects`, `awards`,
    `certifications`, `faq`, `blog`, `brand`.
  - `a11y` — every `sr-only` label enumerated in Context.
  - `blog` — listing `title`, `description`, post-nav labels
    (`previous`/`next`), `readTranslation` (switch-to-translation link).
  - `languageSwitcher` — `label`, `en`, `vi`.
- Replace hardcoded strings: use `useTranslations()` in client components
  (`command-menu.tsx`, `mobile-nav.tsx`, `language-switcher.tsx`) and
  `getTranslations()` in server components (footer, panels, blog pages).
- Drive `MAIN_NAV` titles and command-menu link titles from message keys; keep
  `href` values static (they are locale-agnostic and prefixed by the `Link`
  helper).

### 4. `Localized<T>` helper + vertical slice (`faq.ts`)

- `src/i18n/localized.ts`:
  ```ts
  import type { Locale } from "./routing";
  export type Localized<T> = Record<Locale, T>;
  export function resolveLocalized<T>(value: Localized<T>, locale: Locale): T {
    return value[locale];
  }
  ```
- Convert `faq.ts` first end-to-end: `question`/`answer` become
  `Localized<string>`, still interpolating `USER` fields. Author real
  Vietnamese where trivial; seed the rest with EN + `TODO(i18n)`.
- Update `faq.tsx` (render) and `getFaqJsonLd()` in `(root)/page.tsx` (schema)
  to resolve against the active locale from a single localized source — proving
  render + schema stay in sync. Verify build + both locales before proceeding.

### 5. Migrate remaining prose data + consumers

- Apply the same `Localized<T>` shape to `user.ts` (`bio`, `about`,
  `flipSentences`, `jobTitle`, `jobs[].title`), `experiences.ts` (`title`,
  `employmentType`, `description`), `projects.ts`, `awards.ts`,
  `certifications.ts`. Keep language-neutral fields plain: URLs, dates, logos,
  company names, encoded email/phone, skill tokens, icon keys.
- Thread the active `locale` into each consuming component. Server components
  read `locale` from params/`getLocale()`; the profile section components are
  server components today, so this is mostly passing `locale` down or calling
  `getLocale()` where the data is resolved.
- For markdown fields (`about`, experience `description`), the localized string
  still flows through the existing `<Markdown>` renderer unchanged.

### 6. Locale-aware SEO

- `getWebSiteJsonLd()` and the ProfilePage/FAQPage builders: set `inLanguage`
  from the active locale; the ProfilePage `description`/`jobTitle` resolve from
  the localized `USER`; FAQPage pulls the localized `FAQ`.
- `generateMetadata({ params: { locale } })` on localized routes: set
  `alternates.canonical` to the locale URL and `alternates.languages` to
  `{ en: "/en/...", vi: "/vi/...", "x-default": "/en/..." }`. Use the
  `getPathname` navigation helper to build correct per-locale URLs.
- `sitemap.ts`: for each page emit both locale URLs, each with an
  `alternates.languages` map (en/vi). Keep machine routes as single entries.
- Preserve `metadataBase`, OG, Twitter, and icon config from the current root
  metadata; only add the locale/alternates layer.

### 7. Blog locale pairing

- Extend `PostMetadata` (`src/features/blog/types/post.ts`) with
  `locale: "en" | "vi"` and `translationKey?: string` (shared id across a pair).
- Frontmatter edits: give the existing EN/VI pair the same `translationKey`
  (e.g. `vnx-academy-agentic-rag`) and their respective `locale`. Backfill
  `ai-ecommerce-case-study.mdx` with `locale: "en"` (no `translationKey`).
- `posts.ts`:
  - `getAllPosts(locale)` filters by `metadata.locale`.
  - `getPostBySlug(slug)` unchanged (slug is globally unique).
  - Add `getTranslation(post, targetLocale)` that finds the post sharing
    `translationKey` with the target locale.
  - Normalize: require `locale` in `normalizeMetadata`, defaulting to `en` if
    absent so existing posts don't throw.
- Blog listing + `[slug]` page consume the active locale; the post header shows
  a "Read in Tiếng Việt / Read in English" link when a translation exists,
  routing to the counterpart slug.
- `command-menu.tsx` blog links: filter by active locale.

### 8. Language switcher

- `src/components/language-switcher.tsx` (client): use `usePathname` +
  `useRouter` from `src/i18n/navigation`. On change, `router.replace(pathname,
  { locale: next })` so the same path renders in the new locale; preserve the
  URL hash (read `window.location.hash` and re-append) so section anchors like
  `/#about` survive. For blog posts, if a `translationKey` counterpart exists,
  route to that slug instead of the same slug under the other locale.
- Place it in `site-header.tsx` next to `ToggleTheme`.

### 9. Localize not-found pages

- `not-found.tsx` and blog `not-found.tsx`: replace hardcoded copy with
  `getTranslations()` keys under a `notFound` namespace.

## Risks And Recovery

- **Risk: `always` prefix changes every English URL → SEO/link rot.**
  Mitigation: permanent 301 redirects for `/`, `/blog`, `/blog/:slug`,
  `/internal-project` → `/en/*`; `hreflang` + `x-default` on every page; sitemap
  lists the new `/en` and `/vi` URLs. Prove redirects with the build output and
  a curl of each legacy path.
- **Risk: machine routes accidentally locale-prefixed or redirected.**
  Mitigation: keep them at `src/app/` root (not under `[locale]`); middleware
  matcher excludes them; the legacy redirects target only the four localized
  paths. Prove with curl of `/rss`, `/llms.txt`, `/sitemap.xml`, `/vcard`,
  `/manifest.webmanifest` — all resolve, none redirect to `/en`.
- **Risk: FAQ schema/render drift.** Mitigation: one localized `FAQ` source
  feeds both the visible list and FAQPage JSON-LD; no second copy exists.
- **Risk: client components missing message context / hydration mismatch.**
  Mitigation: `NextIntlClientProvider` wraps all `(app)` children in the
  `[locale]` layout; use `setRequestLocale` in layout + pages for static
  rendering; import navigation only from `src/i18n/navigation`.
- **Risk: root `<html>` duplication when splitting layouts.** Mitigation:
  resolve the exact root-vs-`[locale]` layout split in step 2 and record it in
  Decisions before mass edits; verify no nested `<html>` in the built output.
- **Risk: large data-file churn introduces type errors.** Mitigation: land the
  `Localized<T>` helper + `faq.ts` slice first and verify; `tsc` surfaces any
  unconverted consumer across the rest.
- **No automated test suite exists** — `pnpm build`, `pnpm check-types`,
  `pnpm lint`, `pnpm format:check`, plus a manual smoke of `/en` and `/vi` are
  the safety net.
- **Recovery:** work on a feature branch; commit the route restructure +
  redirects as its own commit so `git revert` is surgical if rollback is needed.
  All prose migrations are additive per file and individually revertible.

## Decisions

- 2026-09-01: Use `next-intl` over a hand-rolled dictionary — App Router locale
  routing, static params, navigation helpers, and a client message provider are
  all needed (multiple `"use client"` surfaces); YAGNI favors not reinventing
  middleware.
- 2026-09-01: `localePrefix: 'always'` — both locales prefixed (`/en`, `/vi`).
  Per user decision (2026-09-01), chosen over `as-needed` for URL clarity and
  symmetric hreflang. Consequence: every legacy English URL gets a permanent
  301 redirect to `/en/*` to preserve existing SEO/GEO ranking.
- 2026-09-01: `defaultLocale: 'en'` — English remains default (per user), which
  matches the existing English-first SEO investment.
- 2026-09-01: Machine/SEO endpoints (`llms`, `rss`, `vcard`, `og`, `manifest`,
  `robots`) stay language-neutral this pass; localizing them is a follow-up.
- 2026-09-01: Vietnamese prose is seeded with English + `TODO(i18n)` markers;
  authoring real translations is the user's content task, not this mechanism
  work.
- 2026-09-01: Exact root-vs-`[locale]` `<html>` layout split to be finalized in
  Approach step 2 and recorded here before mass edits.

Promote lasting product or architecture decisions into `docs/decisions/`.
